2 · Per-chip memory

The vLLM share draws a line across every chip

vLLM's hbm_utilization share is a line at share × 15.75 GiB. When vLLM starts, everything already on the chip (trainer weights) plus vLLM's own weights count against it, and vLLM fills the rest up to the line with KV cache. Everything allocated later lives above the line: optimizer state for full fine-tuning, the training step's activations and logits, and some fixed runtime overhead. vLLM's memory stays put during training.

ComponentWhereFormula (per chip)4B8B14B

Two conditions must hold. vLLM must fit one maximum-length request in its KV pool (prompt cap + completion cap + 256 tokens), or it refuses to start. And the training step must fit above the line: activations + logits + optimizer + 0.3 GiB margin ≤ 15.75 − line − fixed overhead.

3 · Scaling

Training memory by context and chunk size

Per micro-step, each FSDP group holds one sequence per prompt (8 rollouts over 8 groups), so activation memory per chip grows linearly with sequence length and with prompts per micro-step. The fp32 logits are the other big term: without chunking they scale with the completion length; chunking caps them at the chunk size. 5 · Choosing hyperparameters

A procedure for a new workload

  1. Fix the context. Prompt cap + completion cap set both vLLM's minimum KV (one request must fit) and training memory (training pads every sequence to the cap). Don't set the cap far above what completions need: it costs training time even when rollouts stop early.
  2. Pick the chunk. No chunking if logits fit at your context (short contexts); otherwise 512.
  3. Find the share window. Lowest share: vLLM weights + trainer copies + overhead + KV for one max-length request. Highest share: whatever leaves room above the line for the training step. Use the planner's button; it picks the middle of the window, biased toward more KV.
  4. Raise prompts per micro-step as far as the window allows. That is the largest free speedup at short context; at long context it is usually 1.
  5. Check KV concurrency. Each vLLM copy decodes about batch × group ÷ 6 rollouts at once. If its KV pool holds fewer than that many full-length rollouts, vLLM runs them in waves: rollouts slow down but nothing fails. Prefer spending spare memory on KV at long context and on micro-step size at short context.
  6. If it doesn't fit, in order: LoRA instead of full fine-tuning (full adds ~12 bytes per parameter of optimizer and gradient state, ×2 for PPO's critic); GRPO instead of PPO; a shorter cap. For 14B, the structural fix is splitting each vLLM copy over 2 hosts, which halves its ~6.9 GiB per chip; that is not implemented yet.
